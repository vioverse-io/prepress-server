Overview

Connect STS Work Order to PrintReach Midnight so jobs flow between systems instead of being manually re-keyed. This is a SQL Server version feature only -- the M: drive version runs from file:// and cannot make API calls.

UI changes are designed in prepress-mdrive/ first (the design source), then synced to server-sql/ via /prepress-deploy.

How the Two Systems Relate (Joe's Whiteboard, 2026-06-10)

The Work Order app and Midnight serve different purposes and track different statuses.

The Work Order app is a pre-production planning tool

You figure out how to build something -- specs, file paths, instructions, signoffs. When everything is resolved, the plan is complete. This does NOT mean the physical work is done.

Midnight is the production system

Midnight tracks the actual printing, cutting, finishing, and mailing. It has its own statuses independent of the Work Order app.

Status independence

  • "Plan Complete" in the Work Order app does NOT close the job in Midnight.
  • A completed production run in Midnight does NOT mark the Work Order as done.
  • The two systems serve different purposes and their statuses are intentionally independent.

Midnight API -- What We Know

PrintReach Midnight exposes both REST and SOAP APIs at https://api.vsmidnight.com.

ProtocolUse ForDocs
RESTJob lookup, order search, customer dataSwagger: api.vsmidnight.com/swagger
SOAPFile attachments (only way to upload files via API)WSDL: api.vsmidnight.com/service1.asmx

Authentication

REST: Bearer token. Call POST /v1/Token/UserAuthentication with { DomainName, UserName, Password, IsPasswordEncrypted }. Returns { access_token, refresh_token, expires_in }.

SOAP: Uses a DevToken from Admin Settings > Global Settings > Site Token.

Limitations

  • No webhooks. Midnight is request/response only. To detect changes, we'd have to poll with OrderModifiedDate filters.
  • File upload via API is SOAP only. The REST API has no attachment endpoints for orders. But the hot folder approach bypasses the API entirely.
  • Rate limits: Not documented publicly. Ask PrintReach.

What We Want To Do

Feature 1: Job Lookup (Midnight → Work Order)

When creating a new work order, instead of typing job details manually:

  • User enters a 6-digit Midnight job number
  • App calls Midnight's API via our Express server
  • New Job form auto-fills with whatever Midnight returns
  • User reviews, adjusts if needed, saves
  • The Midnight order ID is stored so the two systems stay linked

Feature 2: Send to Hot Folder / PDF Push (Work Order → Midnight)

After planning is complete:

  • User clicks "Send to Hot Folder"
  • Two delivery mechanisms (decide which to implement first):
    • Hot folder (simpler): Server generates a PDF and drops it into a watched network folder that Midnight monitors. Midnight picks it up automatically.
    • SOAP API upload: Server generates a PDF, base64-encodes it, and uploads via SOAP OrderAddAttachment. More control, but more complex.
  • Confirmation toast on success, error message on failure

Feature 3: Reopen Planning (Return from Hot Folder)

If the plan needs revision after being sent:

  • User clicks "Reopen Planning"
  • Removes the file from the hot folder (or resets the planning-resolved flag)
  • Job reopens in the Work Order app for re-planning
  • Does NOT affect Midnight's production status

Feature 4: Linking Existing Jobs

Jobs already in the app have Midnight job numbers typed in by hand. The jobNumber field is already the 6-digit Midnight number -- the natural linking key. Old jobs are NOT excluded.

  • Passive link (recommended first): Just start using the Midnight ID for new features. Old jobs work as-is.
  • On-demand refresh: "Refresh from Midnight" button. Pulls current data, shows a diff, user confirms.
  • Bulk link: One-time script. Risky if formats differ. Defer.

Feature 5: CSR Directory Sync (future)

Pull CSR names from Midnight's user directory instead of hard-coding them in the quick-pick dropdown. Keeps the list in sync automatically.

Data Conflict Resolution

  • On import (new job): Midnight data fills the form. User reviews before saving. Midnight is source of truth for initial data.
  • On refresh (existing job): Show a side-by-side diff. User picks which to keep per field, or "Accept All."
  • Name mismatches: Form auto-fills with Midnight's exact string. Still works (text input, not strict enum).
  • Date formats: Midnight returns ISO dates. Convert to MM/DD/YYYY on the client side.

Server-Side PDF Generation

This is the biggest technical challenge in the integration.

The current print system is 100% browser-based (window.print()). The app never produces an actual PDF file. To send a PDF to a hot folder or upload via SOAP, the server must generate one.

Option A: Puppeteer (recommended)

Server receives the print HTML, Puppeteer renders it in headless Chromium, calls page.pdf(). Pixel-perfect match with browser output. Requires ~500 MB RAM for Chromium.

Option B: Client sends PDF

User saves as PDF from browser print dialog, then uploads. No server dependency, but terrible UX (two manual steps).

Option C: html-pdf-node or pdf-lib

Lighter weight, but limited CSS support. Custom fonts may not render correctly.

PDF Generation Flow (Hot Folder)

1. Client clicks "Send to Hot Folder"
2. Client calls POST /api/midnight/job/:jobNumber/hotfolder
   Body: { printHtml: buildPrintHTML() }
3. Server receives HTML
4. Puppeteer loads HTML, calls page.pdf({ format: 'Letter' })
5. PDF written to HOT_FOLDER_PATH/<jobNumber>_WO.pdf
6. Midnight detects the new file and triggers its workflow
7. Server updates job: planningStatus = 'complete', midnightLastSync = now
8. Client shows toast: "Work order sent to hot folder for Job #123456"

General Principles

  • All Midnight errors are non-fatal. The work order app works fine without Midnight.
  • Network errors retry once automatically, then surface to the user.
  • Auth token cached in memory, auto-refreshed when expired.

Security

  • Credentials server-side only in .env. Never sent to the browser.
  • Input validation: Job number sanitized to numeric only, max 10 digits.
  • HTTPS: Midnight API calls encrypted in transit.
  • Hot folder path: Validated at startup. Path injection prevented by sanitized job number only.
  • No secrets in git: .env in .gitignore.
  • Feature toggle: MIDNIGHT_ENABLED=false disables everything.

Testing Strategy

Development (no Midnight access)

  • Mock API responses with MIDNIGHT_MOCK=true
  • Hot folder points to a local temp directory
  • Full UI flow testable without real credentials

Acceptance Criteria

  • Lookup: enter job number, form auto-fills correctly
  • Lookup: unknown job number shows "not found"
  • Lookup: network failure shows error, manual entry still works
  • Hot folder: PDF appears in the watched folder
  • Hot folder: Midnight picks up the file
  • Reopen: file removed from hot folder, job reopened
  • SOAP (if used): PDF appears as attachment in Midnight
  • PDF output matches browser print visually
  • Toggle: MIDNIGHT_ENABLED=false hides all Midnight UI
  • M: drive version: no Midnight UI, no console errors

Dependencies & Scope

Dependencies

  • SQL Server version deployed first
  • Midnight API credentials from PrintReach admin or IT
  • Hot folder path from IT (Phase 3)
  • Puppeteer/Chromium on the server (Phase 3)
  • npm packages: puppeteer, optionally soap

Not In Scope (Yet)

  • Real-time sync / polling for Midnight changes (no webhooks)
  • Creating jobs in Midnight from the Work Order app
  • Pulling production status or job costing data
  • Inventory or invoicing integration
  • Automatic status sync (statuses are intentionally independent)
